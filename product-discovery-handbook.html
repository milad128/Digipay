1. Discovery scope

Digipay is a BNPL provider in Iran. This discovery defines how merchants integrate Digipay credit products (Wallet, 1pay, 4pay) into e-commerce journeys (PDP, PLP, Checkout), aligned with best practices from Tabby (business/product), Klarna, Afterpay, and Stripe (merchant DX and API patterns).

Current artifact status: More-code segment is fully prototyped (wireframe + final UI + docs). Mid-code and Low-code segments are defined at product level here; UX prototypes are Phase 2.

2. Merchant segmentation

Merchants are classified on three independent attributes. During discovery, treat each combination as a separate segment; merge only when the required service bundle is identical.

AttributeValuesMeaning
Development capacity More code · Mid code · Low code How much native UI and API orchestration the merchant can build on their site.
Trust relationship Trusted · Untrusted Trusted: Digipay returns numeric balances (1pay, 4pay, wallet, debt) for personalized UX.
Untrusted: Merchant sends basket amount; Digipay returns only enough / not-enough per method (no raw figures).
Amount finalization At checkout · After checkout At checkout: Fixed basket amount (e.g. retail). Charge at confirm.
After checkout: Variable final amount (e.g. ride-hailing, services). Authorize → capture flow.

Maximum segments: 3 × 2 × 2 = 12. More-code has 4 sub-segments (Trusted/Untrusted × At/After) — currently prototyped.

3. User levels (L0 / L1 / L2)

Every page load should resolve user level first via GetUserLevel. UX goals differ by level:

LevelStatePrimary UX goalAllowed credit actions
L0 No credit balance Motivate credit application Apply CTA; 4pay/1pay locked at checkout; wallet/IPG/competitors may still be available per policy
L1 Has credit, can purchase Motivate best Digipay payment method 4pay (recommended), 1pay (fast buy), wallet; show breakdown before commit for 4pay
L2 Has outstanding debt Motivate repayment, then credit purchase 4pay/1pay locked until repay; repay CTA prominent; wallet remains available (debt does not block wallet)
Decision (OQ-1): When a user has debt on a credit limit (L2), they can still pay with wallet. Only 1pay and 4pay stay locked until repayment.

4. Payment method conventions

Wallet

  • Debit from wallet balance + cashback rules
  • OTP: required per policy
  • IPG uplift: allowed when balance < basket amount
  • Partial pay: wallet portion + IPG for remainder

1pay

  • Frictionless single-shot credit purchase
  • No OTP (low friction)
  • No IPG uplift — all-or-nothing within available 1pay balance
  • Ideal for “buy now” from PDP

4pay (installment credit)

  • OTP: required
  • IPG uplift: allowed via server formula (not simple A÷4)
  • Formula: creditPayment = min(A, B × 0.75)
  • debitPayment = A − creditPayment (paid via IPG upfront)
  • Installment schedule and due dates must come from Get4PayFormulaBreakdown — never client-calculated

Competitors & fallback (all dev tiers)

  • Checkout must list SnappPay, Tara, and IPG alongside Digipay methods
  • Reduces checkout dead-ends when Digipay credit is insufficient or locked
  • Digipay methods should be visually prioritized when eligible (L1)

5. Trust & finalization policies

Trusted merchants

  • Call GetBalanceAndDebt and GetCreditHeadroom for numeric personalization
  • Show balances on checkout method cards (1pay, 4pay, wallet) to motivate Digipay selection
  • Pass 4pay headroom into formula breakdown request

Untrusted merchants

  • Never call balance/debt endpoints
  • Use GetEligibilityFlagsOnly — merchant posts basket amount, receives enough/not-enough flags only
  • UX labels: “Eligible / Partial / Not eligible” — no numeric amounts

After-checkout (service merchants)

  1. AuthorizeAmount at checkout start (hold capacity, do not capture)
  2. Service completes → final amount known
  3. CaptureFinalAmount for the full final amount (no partial capture)
  4. AdjustOrVoidAuthorization if the trip/order is canceled (void), not for charging less than authorized in increments
Decision (OQ-3): Partial capture is not required. Capture is always for the complete final amount, or void/adjust on cancel.
Decision (OQ-2): Lock at authorize — eligibility and payment method are fixed when AuthorizeAmount succeeds. At capture, Digipay does not re-check user level; capture proceeds if it was valid at authorize (e.g. user may become L2 during the trip but 4pay capture still completes).

7. Design principles & limitations

Do
  • Server-authoritative pricing, installments, and due dates
  • Transparent installment breakdown before payment commitment (Klarna-style)
  • Strong level-based CTAs with clear next action (Afterpay-style)
  • Idempotent checkout sessions; recoverable after refresh
  • Webhook as source of truth for order state
Don’t
  • Calculate 4pay splits as A÷4 on the client
  • Expose numeric balances to untrusted merchants
  • Capture before final amount is known (after-checkout segments)
  • Hide competitor BNPL/IPG at checkout (conversion safety)
  • Allow 1pay when balance < basket (no uplift path)

8. Segment merge guidance (post-discovery)

Merge segments only when all of the following match:

  • Same API service bundle (see service catalog matrix)
  • Same UX component set (only styling/copy may differ)
  • Same compliance and data-exposure rules
Likely merge candidatesRationale
Trusted+At ↔ Trusted+After (same dev tier)Same balance APIs; after-checkout adds authorize/capture only at checkout step
Untrusted+At ↔ Untrusted+After (same dev tier)Same flags API; after-checkout adds auth/capture services

OQ-2 reference (resolved: Option A)

For after-checkout flows, user level may change between authorize and capture (e.g. L1 → L2 mid-trip). Chosen policy: eligibility is locked at authorize; capture does not call GetUserLevel again for method eligibility. Engineering must persist authorizedLevel, authorizedMethod, and eligibility snapshot on the checkout session.
