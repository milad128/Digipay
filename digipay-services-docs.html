BNPL UX Best Practices Applied

Klarna / Stripe style
  • Transparent installment breakdown before commitment
  • Server-authoritative pricing and due-dates (no client math)
  • Recoverable checkout sessions + idempotent APIs
Afterpay / leading BNPL style
  • Strong level-based CTAs: Apply / Pay / Repay
  • Clear lock-state messaging with immediate next action
  • Fallback payment methods to reduce checkout dead-ends

More Code Sub-segment Coverage

Trusted + At checkout
  • Numeric balances shown to user
  • Immediate final charge in checkout
  • Core services + trusted services
Untrusted + At checkout
  • No numeric balance exposure
  • Sufficiency flags only
  • Core services + eligibility-only service
Trusted + After checkout
  • Numeric info allowed
  • Authorize first, capture after final amount
  • Core + trusted + after-checkout services
Untrusted + After checkout
  • Eligibility-only visibility
  • Authorize/capture pattern required
  • Core + untrusted + after-checkout services

Page-Level Integration Sequence

PDP sequence
  • 1) Call GetUserLevel
  • 2) Call GetPaymentOptions(amount) for current SKU price
  • 3) If 4pay eligible, call Get4PayFormulaBreakdown
  • 4) L0 click → CreateCreditApplicationSession
  • 5) L2 click → CreateRepaymentSession
PLP & Checkout sequence
  • PLP: GetUserLevel + BatchPaymentOptions + GetInstallmentPreviewLite
  • Checkout start: CreateCheckoutSession
  • Load methods: GetPaymentOptionsForCheckout
  • User select: SelectPaymentMethod
  • If uplift: InitiateIPGUplift + OTPChallenge
  • Finalize: ConfirmPayment and reconcile with PaymentWebhooks

Service Technical Documentation

GetUserLevel

PDP / PLP / Checkout
EndpointGET /v1/users/me/level
PurposeResolve user state: L0, L1, L2 and debt lock status.
Product logicL0 = apply CTA, L1 = buy CTA, L2 = repay CTA first.
Response { "level": 1, "debtLocked": false, "updatedAt": "2026-05-28T08:30:00Z" }
Engineering: cache short-term (30-60s), re-fetch after return from apply/repay journey.

GetBalanceAndDebt (trusted only)

Trusted variants
EndpointGET /v1/users/me/balance-debt
PurposeReturn numeric wallet/credit/debt amounts for trusted merchant UX rendering.
RuleMust never be called by untrusted sub-segments.

GetCreditHeadroom (trusted only)

Trusted variants
EndpointGET /v1/users/me/credit-headroom
PurposeReturn live credit headroom for 1pay/4pay recommendation logic.
Product logicUse only in trusted mode; pass values into 4pay formula breakdown request.

GetEligibilityFlagsOnly (untrusted only)

Untrusted variants
EndpointPOST /v1/payment-options/flags
PurposeReturn boolean eligibility by method without exposing balances/debt values.
UX outputRender labels like “Eligible / Partial / Not eligible” only.

GetPaymentOptions(amount)

PDP
EndpointPOST /v1/payment-options
Request{ amount, cartRef, userToken }
PurposeDetermine eligibility and recommendation among 4pay / 1pay / wallet.
Trusted policyTrusted gets numeric balances; not-trusted gets sufficiency flags only.
Response (example) { "recommended": "fourpay", "methods": { "fourpay": { "eligible": true }, "onepay": { "eligible": true, "rapidPurchase": true }, "wallet": { "eligible": true, "requiresIPGTopup": true } } }
PM note: this endpoint directly controls conversion UX on PDP (ordering + visibility of payment methods).

AuthorizeAmount (after-checkout)

After checkout variants
EndpointPOST /v1/checkout/sessions/{id}/authorize
PurposeReserve payment capacity before final amount is known (service use cases).
Best practiceNever capture at this step; capture only after final amount settlement.

CaptureFinalAmount (after-checkout)

After checkout variants
EndpointPOST /v1/checkout/sessions/{id}/capture
PurposeCapture the exact final amount after service completion.
RuleValidate captured amount against authorization policy and risk controls.

AdjustOrVoidAuthorization (after-checkout)

After checkout variants
EndpointPOST /v1/checkout/sessions/{id}/adjust-or-void
PurposeAdjust hold or void authorization if final charge is canceled or changed materially.
EngineeringMust be idempotent and audited with reason codes.

Get4PayFormulaBreakdown

PDP / Checkout
EndpointPOST /v1/fourpay/breakdown
FormulacreditPayment = min(A, B*0.75), debitPayment = A - creditPayment
PurposeShow due dates and split based on real 4pay rule (not A/4).
Response (example) { "creditPayment": 16500000, "debitPayment": 2000000, "installments": [ {"index":1,"dueDate":"2026-06-28","amount":4125000}, {"index":2,"dueDate":"2026-07-28","amount":4125000}, {"index":3,"dueDate":"2026-08-28","amount":4125000}, {"index":4,"dueDate":"2026-09-28","amount":4125000} ] }

CreateCreditApplicationSession

L0 journey
EndpointPOST /v1/credit-applications/session
PurposeLaunch apply flow and return user to same merchant page context.
Required fields{ amount, returnUrl, merchantRef }
Engineering: validate returnUrl and keep original page state in merchantRef for seamless resume.

CreateRepaymentSession

L2 journey
EndpointPOST /v1/repayments/session
PurposeStart debt settlement and redirect back to PDP/Checkout after payment.
Required fields{ debtId, returnUrl, merchantRef }
PM note: L2 journey must preserve cart and reduce frustration with clear “repay then continue” messaging.

BatchPaymentOptions(items[])

PLP
EndpointPOST /v1/payment-options/batch
PurposeFetch BNPL badges for many products in one call (performance-critical PLP service).
Integration logicCall by visible items (pagination/viewport), not whole catalog.

GetInstallmentPreviewLite

PLP
EndpointPOST /v1/fourpay/preview-lite
PurposeShow lightweight “from X/month” text on product cards.
RuleOnly teaser output; full legal schedule must come from full breakdown endpoint.

CreateCheckoutSession

Checkout
EndpointPOST /v1/checkout/sessions
PurposeCreate single source of truth for checkout state.
Request{ merchantOrderId, amount, cart, callbackUrl }
Engineering: use idempotency key; all next calls must use this session ID.

GetPaymentOptionsForCheckout

Checkout
EndpointGET /v1/checkout/sessions/{id}/payment-options
PurposeRender final method list for checkout (Digipay + other BNPL + IPG).
RuleLow/Mid/More code all need this list in checkout (per your requirement).

SelectPaymentMethod

Checkout
EndpointPOST /v1/checkout/sessions/{id}/select-method
PurposePersist selected method and return next action (OTP/IPG/breakdown/confirm).
Allowed methodsfourpay | onepay | wallet | snappay | tara | ipg

InitiateIPGUplift + OTPChallenge

Checkout (wallet/4pay)
EndpointsPOST /v1/payments/uplift + POST /v1/otp/challenge
PurposeHandle IPG top-up and OTP verification for secured methods.
Flow orderuplift → return → otp challenge → otp verify → confirm

ConfirmPayment + PaymentWebhooks

Checkout finalize
EndpointPOST /v1/checkout/sessions/{id}/confirm
Webhookspayment.succeeded, payment.failed, repayment.completed
PurposeFinalize payment and reconcile merchant order state reliably.
Engineering: webhook is source of truth; confirmation API response is provisional UI signal.

Developer + Product alignment notes

For product managers
  • Track conversion by level (L0/L1/L2) separately.
  • Track drop-off points: apply start, repay start, OTP fail, IPG fail.
  • Measure method selection share (4pay vs 1pay vs wallet vs competitors).
  • Ensure all payment explanations are transparent before commit.
For engineers
  • Keep checkout session idempotent and recoverable after refresh.
  • Do not calculate financial values client-side in production.
  • Implement robust retry/backoff for network and provider failures.
  • Use webhook signature verification and idempotent order updates.
